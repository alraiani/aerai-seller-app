# AERai Seller Web (seller.aeraigroup.com)

Multi-user web app for AERai Group's Amazon seller operations: source files (Amazon SP-API reports) land untouched in blob storage, are parsed into a staging layer in a centralized SQL Server database, promotes it into curated tables, and exposes reporting views to Razor Pages (dashboard, inventory, orders, advertising, settlements, products/COGS, import tools, user admin).

**Always load the `web-coding-standards` skill before writing or reviewing code here.** It holds the principles, patterns, practices, and commenting standard this solution follows.

Work tracked on the GitHub project board (https://github.com/users/alraiani/projects/3) is logged with the `github-board-updates` skill: move the item and comment on its issue at start, each phase, and finish.

This is the only application in the repository. The earlier WPF desktop app (SQLite, QuickBooks IIF export) was retired and its remaining capabilities — the Orders API and the QuickBooks bookkeeping export — were ported here; its source is kept in git history at the tag `desktop-final`.

## Solution layout

```
AERai.Seller.slnx              # The one solution (named for the repo; it holds the Web projects)
src/
  AERai.Web.Domain/            # Entities: Staging/ (raw), Core/ (curated), Reporting/ (view read models). No references.
  AERai.Web.Application/       # Abstractions, use-case services, DTOs, Result, file parsing. References Domain.
  AERai.Web.Infrastructure/    # AppDbContext, EF configs, migrations (incl. views/procs), queries, SP-API clients, Identity adapters.
  AERai.Web.UI/                # Razor Pages + Program.cs composition root.
tests/                         # xUnit: Application.Tests (pure), Infrastructure.Tests (needs SQL; skips without AERAI_TEST_SQL)
infra/                         # Bicep for Azure (App Service, Azure SQL, Key Vault, App Insights, custom domain)
samples/                       # Example import files
docker-compose.yml             # Local SQL Server 2025 (+ optional containerized app)
```

Dependencies: `UI → Application → Domain`; `Infrastructure → Application`. `UI` references `Infrastructure` **only** from `Program.cs` (`AddInfrastructure`, `InitializeDatabaseAsync`). PageModels never touch `AppDbContext`, `UserManager`, or `SignInManager` — they call Application interfaces (`IIdentityService`, `IReportingQueries`, …).

## Data flow: source → blob → staging → core → views

```
Amazon SP-API reports ─┐  (upload today; automated download later)
                       ▼
   Blob storage  raw/{source}/{yyyy}/{MM}/{dd}/{id}-{file}   ← landing zone, write-once, kept forever
                       │  StagingImportService.StageRawFileAsync (always reads FROM blob)
                       ▼
   stg.*   raw text rows ── core.usp_PromoteImportBatch ──► core.*  typed ──► rpt.vw_*  views ──► pages
```

- **Landing zone** (`IRawFileStore`, Azure Blob Storage; Azurite locally): every accepted file is stored byte-for-byte before parsing, with its SHA-256 recorded on `stg.ImportBatch` (`RawFilePath`, `RawFileSha256`). Blobs are never overwritten.
- **Staging reads from the blob, never from the upload stream**, so uploads, re-staging (`RestageAsync`), and future machine ingestion all share one path. A future SP-API worker should: download report → `IRawFileStore.SaveAsync` (path from `RawFilePaths.Build`) → `StageRawFileAsync`.
- Files that fail parsing stay in the landing zone (audit) but create no batch.
- **Data range on batches** (`stg.ImportBatch.DataStart`/`DataEnd`, set by `stg.usp_SetBatchDataRange` right after staging and shown as *Data covers* on the batch list and details): the dates the file's data covers, read from the staged text with the same `stg.ufn_TryParseDateTimeOffset` promotion uses, so a date that promotes also counts. Orders = earliest to latest purchase-date; settlements = the header row's settlement period (else the lines' posted dates); generic inventory = the snapshot dates; FBA inventory/reserved/restock snapshots carry no dates, so their range is the day the batch was received. Unreadable dates are ignored and an all-unreadable file has no range. It is **display only**: the dashboard's "enough history to compare" check and the backfill "already covered" warning deliberately still look at sync-run windows, not batch ranges, because an orders report pulled by *last update* contains old orders whose purchase dates would make a recent pull look like deep history.
- Path layout is an Application concern (`RawFilePaths`); the store itself never interprets content.

## Amazon SP-API ingestion (scheduled pulls)

- **Schedules are data, managed in the app** (Tools → Amazon sync, Operator role): `ops.SyncSchedule` rows with interval (min 15 min, optionally limited to **active hours** `ActiveFrom`–`ActiveUntil` local time, wrapping past midnight when the end is earlier; outside them the next run moves to the window's start) or daily-at-local-time + IANA time zone, lookback, auto-promote, enabled. Next-run math is `ScheduleCalculator` (DST-safe, unit-tested). Default schedules are seeded **disabled**; Orders defaults to **every 4 h** (migration `AddScheduleActiveHours` moved existing faster Orders schedules to 240 min) because hourly pulls keep the database awake — fresher data is a Run now away. Deleting a schedule is a **soft delete** (`DeletedAt`, EF global query filter): run history and the `ops.IngestedReport` ledger must survive, so use `IgnoreQueryFilters()` only where deleted schedules are wanted (Deleted tab, run-history labels, seeding). **Pause all** is the single-row `ops.SyncSettings.IsPaused`; it stops scheduled slots only (Run now / backfills still run) and never flips schedules' own switches.
- **Worker**: `SyncSchedulerWorker` (hosted service) does one thing at a time: runs due schedules and "Run now" requests, and checks on waiting runs. Due slots are claimed with a compare-and-swap on `NextRunAt`, so multiple instances never double-run. History is `ops.SyncRun`; `ops.IngestedReport` guarantees an Amazon report is ingested once.
- **No polling the database (cost)**: Azure SQL is serverless and only auto-pauses after `autoPauseDelay` (15 min, the minimum) without any query; the first request after a pause waits while it resumes. So the worker never ticks. It sleeps until the earliest of the next enabled `NextRunAt` (ignored while paused), the next waiting run's `NextCheckAt`, or `Ingestion:SchedulerMaxSleep` (6 h). It is woken early through `IManualRunChannel`: Run now / backfill enqueue, and **any change to when schedules run must call `Wake()`** (`SyncScheduleService` does this for create, edit, enable, delete, restore, and pause). Never add a background loop that queries SQL on a short fixed interval.
- **Flow**: `ReportIngestionService` → `IAmazonReportsGateway` → `IRawFileStore.SaveAsync` → `StageRawFileAsync` → optional `PromoteAsync`. Same path as uploads from the blob onward.
  - **Requested reports** (everything but settlements) are two steps, so nothing waits in memory. `RunAsync` calls `createReport` and saves the report on the run (`PendingReportId`, `NextCheckAt`, `PollAttempts`; the run stays `Running`). `ContinueAsync` then does one `getReport` per check. While Amazon is still generating, the delay between checks doubles from `ReportPollInterval` up to `ReportPollMaxInterval` (30 s → 1 m → 2 m → 4 m → 5 m), and the run fails after `ReportMaxWait` (counted from the request, `SyncRun.ReportRequestedAt`). Once ready, it downloads, stages, promotes, and completes the run. A `FATAL` report's run message includes Amazon's reason, read from the error document Amazon attaches (`FailureReason`; best effort).
  - **Request cooldown** (`AmazonReportType.RequestCooldown()`, the near real-time FBA reports — FBA inventory and FBA reserved inventory: 30 min): Amazon accepts a repeat request inside its limit and then fails it as `FATAL`. So a run asking sooner than the last request (any run, same report type and marketplace) + cooldown + 1 min doesn't call Amazon: it waits with `NextCheckAt` set and no `PendingReportId`, and `ContinueAsync` requests when the time comes. If another run of the schedule is already waiting to request, the new run ends as NoData without asking. The waiting run's message says until when (`ReportRequestCooldown.Describe`, cleared once it asks), and Run now / Sync all warn at click time from the same rule (`RequestWait`). "Waiting" everywhere (due checks, `HasPendingAsync`, abandoned-run cleanup) means `NextCheckAt` is set, not `PendingReportId`.
  - **Settlements** are listed, not requested, and finish inside `RunAsync`.
  - **Orders API** (`AmazonReportType.OrdersApi`, not a report: `IsReport()` is false) pages through `GET /orders/2026-01-01/orders` (`searchOrders`; `IAmazonOrdersGateway` → `OrdersApiClient`, operation `orders.searchOrders`, 0.0056 req/s burst 20) inside `RunAsync`, which returns each order with its items inline. Each JSON page lands in raw storage under `ordersapi/`, then `IAmazonOrderRepository.UpsertAsync` writes its orders straight to `core.Order`/`core.OrderItem` **as each page arrives** (no staging or promotion; a failed or cancelled run keeps earlier pages, and the next run's overlap fills the rest). A scheduled run asks for orders **updated** since the last success minus the usual overlap (`lastUpdatedAfter`, so status changes on older orders arrive); a backfill asks for orders **created** in its range (`createdAfter`/`createdBefore`, the end held `DataEndSafetyMargin` = 5 min behind now: Amazon 400s on a `createdBefore` less than 2 minutes before its own clock) and, unlike report backfills, has **no 30-day cap** (the cap is Amazon's limit for one report) — Amazon requires exactly one of `createdAfter`/`lastUpdatedAfter` and the same filter on every page. The request must ask for `includedData=FULFILLMENT`: without it Amazon returns only ids, times and items, no `fulfillment` block, so every order would be stored as `Unknown` (and cancelled orders would count as sales). Statuses (`PENDING_AVAILABILITY`, `PENDING`, `UNSHIPPED`, `PARTIALLY_SHIPPED`, `SHIPPED`, `CANCELLED`, `UNFULFILLABLE`) are normalized to the report's spelling (`SHIPPED` → `Shipped`, `PARTIALLY_SHIPPED` → `Partially Shipped`) so `Cancelled`/`Pending` mean the same whichever way an order arrived. An existing order keeps its marketplace, items are updated or added by SKU and never removed (like promotion), unknown SKUs join `core.Product` (existing titles/ASINs are never overwritten), `LastImportBatchId` is `0`, and the write asks for a stock-alert refresh. The marketplace id is sent in the request, so unlike the report there is no cross-marketplace spill. It is an alternative to the Orders report schedule, not an addition: enable one or the other (both write the same orders, so running both is harmless but wasteful); the dashboard treats either as the "Orders" sync.
  - **AWD inventory** (`AmazonReportType.AwdInventory`, not a report: `IsReport()` is false) pages through `GET /awd/2024-05-09/inventory` (`IAmazonAwdGateway` → `AwdApiClient`, operation `awd.listInventory`) inside `RunAsync`. Each JSON page lands in raw storage under `awdinventory/`, then `IAwdInventoryRepository.ReplaceSnapshotAsync` replaces the marketplace's `core.AwdInventorySnapshot` rows for the run's UTC date in one transaction, after every page is read. It writes straight to `core` (no staging or promotion: the JSON is already typed), adds SKUs unknown to `core.Product`, and skips all-zero SKUs. A snapshot like FBA inventory, so no backfill. AWD only operates in the US, so the disabled default schedule (daily 6:05 AM) is seeded for US only.
  - **Deferred transactions** (`AmazonReportType.DeferredTransactions`, not a report: `IsReport()` is false; a snapshot, so no backfill) list what Amazon still holds back through `GET /finances/2024-06-19/transactions?transactionStatus=DEFERRED` (`IAmazonFinancesGateway` → `FinancesApiClient`, operation `finances.listTransactions`, 0.5 req/s burst 10) inside `RunAsync`. Amazon defers nearly every order under its delivery-date policy (`DD7`: paid out about 7 days after delivery; `B2B`: invoiced orders), and a deferred sale is in **no settlement report** until released, when it arrives as ordinary order lines in a later settlement. Every deferral carries Amazon's **`SETTLEMENT_ID`: the settlement the sale was made in** (its period has the sale, its payout does not; Amazon pays it in a later one) and its products (each item's `ProductContext` sku/asin/quantityShipped, item total, `ProductCharges` principal), kept as `core.DeferredTransaction.SettlementId` and `core.DeferredTransactionItem`. A run reads **two listings** — `DEFERRED` (what is held) and `DEFERRED_RELEASED` (what was released, the history) — landing every page under `deferred/`; only once **every** page of both is read does `IDeferredTransactionRepository.ApplyAsync` write them in one transaction: held rows upserted as Deferred, released rows as Released (a release Amazon listed before is history and is not rewritten), and any stored deferral in neither listing marked Released (at its maturity date once passed, else when noticed). Each written transaction's items are replaced. The held listing always reaches back `DeferredListingAge` (179 days; Amazon returns nothing past 180) so nothing still held looks released. The released listing reaches back the same until the marketplace has Amazon-listed releases (`HasReleaseHistoryAsync`), then starts `ReleasedOverlap` (60 days, for B2B invoices; Amazon filters by posted date, not release) before the last success. A failed or partial run writes nothing. A disabled default schedule (daily 7:15 AM) is seeded per marketplace. Amazon keeps a transaction listed as deferred for a day or so after its maturity date, so passed dates show as **Due**.
  - **Ads spend** (`AmazonReportType.AdsSpend`, not SP-API: `IsReport()` is false; not a snapshot, so it backfills) is Sponsored Products spend from the **Amazon Ads API** (reporting v3, `spAdvertisedProduct`, `groupBy advertiser`, `timeUnit DAILY`, `GZIP_JSON`: spend, impressions, clicks, and 7-day attributed sales/orders/units per SKU, campaign, and day). Settlements only carry ad charges as lump-sum SKU-less "Cost of Advertising" lines, which is why it needs this API. It is **requested like a report**: `RunAsync` works out the days (the marketplace's local days; Amazon Ads dates by the profile's time zone, Pacific for US/CA profiles, so runs end **yesterday** — a day the profile hasn't reached is refused) and calls `IAmazonAdsGateway.RequestSpendReportAsync`, the run waits (`PendingReportId`/`NextCheckAt`, the same doubling delay; `Ingestion:AdsReportMaxWait` 3 h because Ads reports are slow), and `ContinueAsync` branches on the type: once `COMPLETED` it lands the gzip **as Amazon served it** under `adsspend/` (metadata `datastart`/`dataend`), reads it back from the blob through `AdSpendReportParser` (rows split by ad group are summed per day/SKU/campaign), and `IAdSpendRepository.ReplaceRangeAsync` **replaces** those days in `core.AdSpend` (unknown SKUs join `core.Product`). A scheduled run starts `AdsAttributionOverlapDays` (14) before the last success's end, because Amazon keeps revising attributed sales, or its lookback on the first run, through yesterday; a backfill's end is exclusive. Every run starts no earlier than `MaxAdsReportAge` (94 days; Amazon keeps 95) and covers at most `MaxAdsReportDays` (31): a schedule left off longer catches up on the latest 31 days, a backfill keeps its start, single backfills wholly older than 95 days are refused, and Backfill all starts Ads spend at the limit with a note (`SyncScheduleService.HistoryLimit`, shared with the settlements 90-day rule). A disabled default schedule (daily 5:45 AM, lookback 14) is seeded per active marketplace.
  - **Stopping a run** (Tools → Amazon sync, *Stop* on a running or waiting run in Last run and in Run history; `IReportIngestionService.StopAsync`): a run **waiting on Amazon** is claimed with the same compare-and-swap on `NextCheckAt`, ended as `SyncRunStatus.Cancelled` (shown as *Stopped*, grey; never a failure or a success, so the schedule's last-success marker doesn't move), and Amazon is asked, best effort, to stop making its report (`IAmazonReportsGateway.CancelReportAsync` → `reports.cancelReport` `DELETE /reports/2021-06-30/reports/{id}`, which Amazon only honours while the report is `IN_QUEUE`; Ads spend: `IAmazonAdsGateway.CancelSpendReportAsync` → `DELETE /reporting/reports/{id}`); the cooldown still counts the request. A run this instance is **executing** (paging the Orders API, AWD, deferred transactions, listing settlements, downloading) is tracked by `IRunStopSignal` (`RunAsync`/`ContinueAsync` link its token with shutdown) and ends after the call in progress, keeping what it already saved, like a failure would (Orders API pages already written stay; AWD and deferred write nothing until every page is read). Another instance's working run can't be stopped from here (the message says to try again). A check that finishes after a stop can't overwrite it: `ISyncRunRepository.CompleteAsync` only completes a run still `Running`. **Cancel N queued** in the toolbar drops Run now / Sync all / backfill requests (every marketplace's: it is one inbox) still in the in-memory inbox (`IManualRunChannel.CancelQueued`, `ISyncScheduleService.CancelQueued`; the channel allows several readers for this).
  - Waiting checks are claimed with a compare-and-swap on `NextCheckAt` (15 min lease). A shutdown mid-check leaves the run waiting and due now, so a restart resumes it. A scheduled slot is skipped while its schedule's previous run is still waiting.
  - Runs left `Running` and not waiting for over an hour (killed mid-request) are failed as interrupted.
- **All SP-API HTTP goes through `SpApiPipelineHandler`** (LWA token via `LwaTokenProvider`, per-operation token buckets in `SpApiRateLimiter`, retry/backoff on 429/5xx, one refresh on 401/403, structured logging without secrets). Never create another `HttpClient` that calls `sellingpartnerapi-*.amazon.com`. Report documents are downloaded with a separate client that never sends the access token (pre-signed S3 URLs). **Connection failures** (no response) are retried by the same backoff (`SpApiRetry.IsTransientConnectionFailure`): DNS/TCP/TLS failures for any request (nothing was sent), a connection dropped mid-request only for GETs — never a `createReport` POST, which may already have reached Amazon and would trip the request cooldown. The LWA token and document clients get the same rule through `SpApiConnectionRetryHandler`.
- **All Amazon Ads HTTP goes through `AdsApiPipelineHandler`** (Infrastructure `AmazonAds/`: bearer token from `AdsTokenProvider`, its own LWA cache per region; `Amazon-Advertising-API-ClientId` and `-Scope` = profile id headers; retry/backoff on 429/5xx honoring `Retry-After`, connection retries by `SpApiRetry`'s rules, so a dropped `createReport` POST is never resent; one refresh on 401). No token buckets: Ads throttles dynamically. `AdsApiClient` creates/reads reports (a 425 "duplicate of" response takes the report Amazon is already making) and downloads them on a separate token-less client (pre-signed S3). The advertising **profile is found per marketplace** from `/v2/profiles` (`accountInfo.marketplaceStringId`, seller account first; cached 6 h in `AdsProfileCache`), so no profile id is configured; a marketplace without one fails its run naming it. Hosts: `AmazonAds:Endpoint` (NA) / `AmazonAds:EuropeEndpoint` (UK); optional `AmazonAds:EuropeRefreshToken` when the EU account was authorized separately. `AmazonAds:Mode` is `Disabled` (default) / `Simulated` (Development: `SimulatedAdsGateway`, four catalog SKUs in two campaigns, ready at the second check) / `Live` (Azure).
- **Modes** (`SpApi:Mode`): `Disabled` (default), `Simulated` (Development: `SimulatedReportsGateway` generates realistic files so the pipeline works without credentials), `Live` (Azure). Credentials `SpApi:ClientId/ClientSecret/RefreshToken` come from user-secrets or Key Vault only.
- **Regions**: SP-API credentials are per region. `SpApi:Endpoint`/`SpApi:RefreshToken` are North America (US, CA); `SpApi:Europe:Endpoint`/`SpApi:Europe:RefreshToken` are Europe (UK), sharing the same LWA client id/secret. Typed clients tag each request with the marketplace's region (`SpApiOperation.RegionKey`), so `LwaTokenProvider` caches a token per region and `SpApiRateLimiter` keeps buckets per (region, operation). A region without its refresh token fails the run with a message naming the missing key; nothing is sent to Amazon.
- **Settlements are limited to the last 90 days.** `getReports` rejects a `createdSince` older than 90 days with a 400 ("RequestedFromDate … is more than 90 days old"), so a listed run starts at most `ReportIngestionService.MaxListingAge` (89 days) back and says so in its message; "Backfill all" starts settlements at that limit (with a note) and fails if the whole range is older, and a single-schedule settlement backfill that ends before the limit is refused. For older settlements, download the flat file V2 from Seller Central (Reports → Payments), upload it to `settlements/yyyy/MM/dd/` in the raw container, and use Tools → Refresh from blobs.
- **The sync page** (`Pages/Tools/Schedules/Index`) lists schedules in one section per `SyncCategory` (`AmazonReportType.Category()`: Orders; Inventory & restock — FBA, reserved, AWD, restock, inventory planning; Settlements & payments — settlements, deferred; Advertising), each with its on/failing counts and a select-all box; the chosen sort applies inside each section, and tag colors come from the category. **Run now, Backfill, Sync all, and Backfill all return to the list** (never the run history): a `SyncQueued` TempData flag makes it refresh every 10 s right away, and it keeps refreshing while any latest run is `Running` (a run waiting on Amazon — `NextCheckAt` set — shows *Waiting on Amazon*).
- **Sync all / Backfill all** (Tools → Amazon sync toolbar, `ISyncScheduleService.SyncAllAsync`/`BackfillAllAsync`): one click queues work for every **switched-on** schedule in an active marketplace, then you can leave the page. *Sync all* is a normal run of each (like Run now), skipping a schedule whose previous run is still waiting on Amazon. *Backfill all* takes one date range and queues it for every enabled schedule that has history (inventory/restock/AWD snapshots are excluded): report-based schedules get one run per 30 days (`BackfillSplitter`), the Orders API gets the whole range in one run and is queued **last** because the scheduler does one thing at a time and that run is the slowest. At most `MaxBackfillAllRuns` (90) runs per click (the manual-run inbox holds 100 and waits when full). Both only queue; progress is in the run history. A single-schedule or "all" backfill whose range an earlier finished backfill (same report type and marketplace, end within a day) already covers is still queued but **warns** that it repeats Amazon calls (`FindCoveringBackfillAsync`); nothing is ever refused for being a repeat.
- **Refresh from blobs** (Tools → Refresh from blobs, `IBlobRefreshService`): loads the database from files already in the raw container **without calling Amazon** — upload report files or Orders API pages (Storage Explorer, `az`), then refresh. It lists the container once and, oldest first (at most `MaxFilesPerRefresh` = 500 per click), loads: report files in `orders/`, `settlements/`, `inventory/` through `IStagingImportService.StageRawFileAsync` then `PromoteAsync` (promotion optional), Orders API pages in `ordersapi/` through `OrdersPageParser` (shared with the live client) and `IAmazonOrderRepository`, and Ads spend reports in `adsspend/` through `AdSpendReportParser` and `IAdSpendRepository` (the days in the blob's `datastart`/`dataend` metadata, else its first to last row). Hand-uploaded files use the marketplace selected in the top bar unless their blob metadata has `marketplaceid`. A file is "already loaded" when an import batch was staged from its path or it is in the `ops.AppliedBlob` ledger (Orders API pages and empty report files, which leave no batch); an Orders API page or Ads spend report the app saved itself (metadata `syncrunid`) was applied on arrival and is skipped. *Reprocess* ignores all that to rebuild a fresh database from the raw files (it adds new batches). Snapshot folders (`fbainventory/`, `fbareservedinventory/`, `fbarestockrecommendations/`, `awdinventory/`, `deferred/`) are **never** loaded: they are dated by the batch's receive day, so an old file would be dated today. One bad file is reported and does not stop the rest. `IRawFileStore.ListAsync` is the only listing API; `scripts/export-raw.sh` is the reverse direction (blobs → files on disk).
- **Restock recommendations**: `GET_RESTOCK_INVENTORY_RECOMMENDATIONS_REPORT` (`AmazonReportType.RestockRecommendations`, a snapshot) → `stg.FbaRestockRow` (`Merchant SKU`, `Recommended replenishment qty`, `Recommended ship date`, `Recommended action`; title-case headers normalize to `merchant-sku` etc.) → `core.RestockRecommendation`, keyed by (marketplace, SKU). Each report is Amazon's complete current advice, so promotion **replaces** the marketplace's rows; an unparseable ship date means "no date", a bad quantity rejects the row. Exposed on `rpt.vw_InventoryPosition` as `AmazonRecommendedQuantity`/`AmazonRecommendedShipDate`. A disabled default schedule (daily 6:30 AM) is seeded per marketplace.
- **Inventory planning (stock age & excess)**: `GET_FBA_INVENTORY_PLANNING_DATA` (`AmazonReportType.FbaInventoryPlanning`, a snapshot; `ImportSource.FbaInventoryPlanning`, raw folder `fbainventoryplanning/`, never loaded by Refresh from blobs) → `stg.FbaPlanningRow` (`FbaPlanningRowMapper`: only `sku`, `inv-age-0-to-90-days`, `estimated-excess-quantity` required, since Amazon renames this report's columns; the `estimated-ais-*` bands are added up into one aged-inventory surcharge) → `core.InventoryHealth` keyed by (marketplace, SKU): age buckets, `EstimatedExcess`, days of supply, next month's storage cost and surcharge. Promotion (V022) **replaces** the marketplace's rows, skips rows whose `marketplace` column names another marketplace (`SkippedRowCount`), and rejects unreadable unit columns. `rpt.vw_InventoryPosition` exposes `AgedUnits` (over 180 days), `EstimatedExcess`, `AgedSurchargeNextMonth`, `StorageCostNextMonth`, `HealthSnapshotDate` (NULL when the SKU isn't in the latest report). A disabled default schedule (daily 6:40 AM) is seeded per marketplace.
- **Inventory reports**: `GET_FBA_MYI_ALL_INVENTORY_DATA` (FBA inventory: available, unsellable, reserved total, inbound working/shipped/receiving) and `GET_RESERVED_INVENTORY_DATA` (FBA reserved inventory: reserved split into customer orders / FC transfers / FC processing; header names have underscores, which header normalization turns into hyphens). Both are snapshots dated by the batch's UTC receive date, so neither can be backfilled (`AmazonReportType.IsSnapshot()`). Promotion keeps them consistent in either order: the reserved report replaces that date's reserved states, and the main report never overwrites an existing reserved breakdown. Default schedules are seeded per missing (marketplace, report type), disabled.
- **Per-marketplace pulls**: every schedule targets one marketplace. `createReport` sends that marketplace id and the simulator generates each marketplace's own channel, currency, and order ids. `getReports` (settlements) sends it too, but **Amazon ignores it for settlements**: every marketplace of a region lists the region's payouts (North America: USD, CAD, and MXN, each its own settlement), so whichever NA schedule ran first used to take them all under its own marketplace. Settlements are therefore staged under `core.Marketplace.SettlementMarketplaceId` (seeded CA → US; `null` = its own), by `ReportIngestionService` and by Refresh from blobs alike: **all North America payouts live in the US list**, tagged by currency and converted into USD (see *Exchange rates*). The simulator lists the region's payouts the same way. Amazon's orders report ignores the marketplace and returns every marketplace in the region (a CA request returns the same Amazon.com, Amazon.com.mx, and Non-Amazon lines as US), so promotion **skips** lines whose `sales-channel` is another marketplace's (counted in `stg.ImportBatch.SkippedRowCount`, not rejected); each marketplace's own schedule promotes its lines.

## Database: one centralized DB, five schemas

| Schema | Role |
|---|---|
| `stg` | Raw imports. `stg.ImportBatch` + one table per source (`OrderLine`, `InventoryRow`, `FbaInventoryRow`, `FbaReservedRow`, `FbaRestockRow`, `FbaPlanningRow`, `SettlementLine`). All business columns are `nvarchar`; every row is kept with its `RawLine` and an `ErrorMessage` after promotion. |
| `core` | Curated, typed, constrained tables (`Marketplace`, `Product`, `ProductCost`, `ProductFamily`, `HomeStock`, `HomeStockMovement`, `LeadTimeProfile`, `RestockRecommendation`, `InventoryHealth`, `Order`, `OrderItem`, `InventorySnapshot`, `AwdInventorySnapshot`, `AdSpend`, `Settlement`, `SettlementLine`, `SettlementExchangeRate`, `DeferredTransaction`, `BookkeepingAccountMapping`, `BookkeepingSettings`, `BookkeepingExport`). Written **only** by `core.usp_PromoteImportBatch`, the AWD, Orders API, deferred transactions, and Ads spend syncs (`AwdInventorySnapshot`; `Order`/`OrderItem`; `DeferredTransaction`; `AdSpend`), the settlement exchange-rate service (`SettlementExchangeRate`), and the user tools (Products/COGS; Inventory edit, home stock, lead times; settlement rate adjustments; the three Bookkeeping tables) — `Marketplace` is seeded reference data. |
| `rpt` | SQL views over `core` (`vw_SalesLine`, `vw_DailySalesBySku`, `vw_OrderSummary`, `vw_InventoryPosition`, `vw_SettlementSummary`, `vw_SettlementSkuSummary`, `vw_SettlementLine`; `vw_SettlementRate` is used by the other settlement views only) mapped as EF keyless entities. Pages read these. |
| `ops` | Ingestion schedules, run history, the ingested-report ledger, the loaded-raw-file ledger (`AppliedBlob`), and stock alerts (`StockAlert`, `StockAlertRead`). |
| `auth` | ASP.NET Core Identity tables. |

Flow: **upload → `stg` (raw) → promote proc (TRY_CONVERT + MERGE, idempotent) → `core` → `rpt` views → pages.** Views and the proc are created in migrations with `migrationBuilder.Sql` and must have matching `Down` SQL. When changing a view/proc, add a new migration that `CREATE OR ALTER`s it — never edit an applied migration.

Locally SQL Server and Azurite run in Docker (`docker compose up -d`). SQL Server uses the named volume `sql2025data` (fixed name, shared with the equivalent `docker run` command), so data survives container rebuilds.

Integration tests (`tests/AERai.Web.Infrastructure.Tests`) run only when `AERAI_TEST_SQL` (server connection string, no database), `AERAI_TEST_BLOB` (e.g. `UseDevelopmentStorage=true`), and/or `AERAI_TEST_MAILPIT` (e.g. `http://localhost:8025/`) are set; each test class creates and drops its own database / container. Without `AERAI_TEST_BLOB`, SQL tests use an in-memory raw store.

## Auth

ASP.NET Core Identity (email = username), cookie auth, no self-registration; sign in with a password or an emailed one-time code. Roles: `Admin` (users + everything), `Operator` (imports, promotion, Amazon sync schedules, COGS edits), `Viewer` (read-only). Every page requires login by default; the anonymous pages are `Account/Login`, the forgot/reset-password pages, and `Account/LoginWithCode`/`VerifyCode`. `/Tools` and `/Bookkeeping` require Operator, `/Admin` requires Admin.

## Marketplaces (US / CA / UK)

- **Reference data**: `core.Marketplace` (seeded: US `ATVPDKIKX0DER`, CA `A2EUQ1WTGCTBG2`, UK `A1F83G8C2ARO7P`) holds each marketplace's currency, time zone, `sales-channel` value, SP-API region, `IsActive`, and `SettlementMarketplaceId` (whose settlements list holds its payouts; CA → US). UK is in the EU region and needs its own SP-API authorization (`SpApi:Europe:RefreshToken`); it was seeded **inactive** and is switched on by migration `ActivateUkMarketplace`, so every environment needs that token. Default schedules for a newly active marketplace are seeded (disabled) at the next app start.
- **Every record has a marketplace**: `stg.ImportBatch`, `core.Order`, `core.InventorySnapshot`, `core.Settlement`, `ops.SyncSchedule`, and `ops.SyncRun` carry a non-null `MarketplaceId`. Promotion stamps the batch's marketplace on what it writes; uploads choose one on the Import page, schedules have one each. `core.Product` is a shared SKU catalog, but **cost of goods is per marketplace** in `core.ProductCost` (no row = not set).
- **Channel guard**: promotion rejects order lines whose `sales-channel` belongs to another marketplace (blank = the batch's own), so a mixed file can never leak orders into the wrong marketplace.
- **Inventory is never pooled**: each marketplace has its own fulfillment network, so snapshots and `rpt.vw_InventoryPosition` are keyed by (marketplace, SKU).
- **The switcher**: `_MarketplaceSwitch` in the top bar posts to `/Marketplace/Switch`, which remembers the choice per user/browser in the `AERai.Marketplace` cookie (`IMarketplacePreference`). Pages get their marketplace from `ICurrentMarketplace` (Application), which falls back to the first active marketplace if the cookie is missing, unknown, or inactive. Every marketplace-scoped query takes a `marketplaceId`; never add a page query that reads across marketplaces.

## Settlement drill-down (Settlements pages)

- Three levels: **Settlements** list (`/Settlements`: totals tiles for what's listed, search by settlement id or any order id / SKU / ASIN / title inside it, period-end date range in the marketplace's local days, a *Paid in* currency filter, sortable amount columns, an **Ad costs** column and card (see *Ad costs* below); the US list holds every North America payout, so CAD and MXN settlements carry a **CA/MX pill** (`SettlementOrigin`, from the currency), every amount, sort, and tile is **in USD** (converted, see *Exchange rates*) with an *As paid* column showing the original net, and settlements still without a rate show "No rate yet" and are counted apart instead of added to the tiles; the search finds settlement ids on the `core` tables first, then filters the view by that list, because testing it inside the view query took seconds per query) → **Summary** (`/Settlements/Summary/{id}`: one row per settlement, SKU, sale price, currency, with Sales / Refunded sales / Refunded expenses / Shipping / FBA fees / Commission / Other expenses / Reserve / Net and the product's ASIN; hovering an *Other expenses* amount lists its charges (`SettlementOtherExpenses` over `IReportingQueries.GetSettlementOtherExpensesAsync`: labelled by kind, largest first, at most 8); views All / With refunds / No SKU, sortable) → **Lines** (`/Settlements/Lines/{id}?sku=&price=`: a totals row equal to the summary row, stuck under the header, then one collapsible group per **order** — lines without an order are grouped by **transaction type** — each expanding into its lines with one signed **Amount** and a category pill; search and the category filter (`?category=`) select whole groups, and paging counts groups so an order is never split). Blank `sku`/`price` select the row of amounts with no SKU (service fees). Filters and sorts are `SettlementListFilter` / `SettlementSkuFilter` / `SettlementLineFilter` (Application `Settlements/`, natural directions in `SettlementSorts`), applied by `IReportingQueries`; expand/collapse is `[data-expand-row]` / `[data-expand-all]` in site.js (lines show without script).
- **Exchange rates** (CAD/MXN → USD): a settlement in another currency than its marketplace's converts at the rate for its **deposit date** (`deposit-date` is kept on `stg.SettlementLine`/`core.Settlement.DepositDate`, set by the proc; migration `AddSettlementExchangeRates` backfilled it from the header rows' raw lines; no deposit date → period end). `core.SettlementExchangeRate` (one row per such settlement) holds the feed's `MarketRate`/`MarketRateDate`/`MarketSource` and an Operator's `ManualRate` (+ `ManualHomeAmount` when they entered the amount that reached the bank, which then **is** the converted payout exactly); the Operator's rate wins. `rpt.vw_SettlementRate` is the **only** place that rule lives (rate 1 in the marketplace's own currency, `NULL` while no rate is known — never guessed); the three settlement views add `HomeCurrency`, `ExchangeRate`, and `Home*` columns from it (the summary converts totals, not rounded lines, and `HomeExpenses` takes the remainder so the four add up to `HomeNet`; per-SKU rows and single lines can differ by a cent). The feed is `IExchangeRateProvider`: `ExchangeRates:Mode` `Live` (default; Frankfurter API = ECB reference rates, free, no key, own `HttpClient`), `Simulated` (fixed rates; integration tests), `Disabled`. Rates are fetched **without polling**: after every Settlements promotion (`SqlPromotionService` → `ISettlementExchangeRateService.FillMissingAsync`; a failure is logged, never fails the promotion) and by the Operator button **Fetch missing rates** on the list; a deposit date still in the future waits (no published rate yet). Operators adjust a rate on the Summary page (`/Settlements/Rates` handlers: Set by amount received or rate, Reset to the daily rate); rules and validation are in `SettlementExchangeRateService`. Summary and Lines show a conversion banner and an **In USD | As paid** switch (`?amounts=Original`, `SettlementAmounts`; `SettlementMoney` picks the shown amounts, falling back to as-paid without a rate). The dashboard's latest payout uses the converted net and the origin pill.
- `rpt.vw_SettlementLine` is the **only** place the bucket and category rules live; `vw_SettlementSummary` and `vw_SettlementSkuSummary` are built on it so all three pages add up to the same payout. Change the rule there, in a new migration.
- **Columns are Seller Central's statement** (migration `MatchAmazonStatementColumns`, checked to the cent against Seller Central): **Reserve** = amount descriptions `Previous Reserve Amount Balance` / `Current Reserve Amount` (account level reserve); **Refunds** = transaction types `Refund…`; **Sales** = `Order…` lines with amount type `ItemPrice` or `ItemWithheldTax` (collected and withheld tax cancel) plus positive `FBA Inventory Reimbursement`s; **Expenses** = everything else (fees, promotions, FBA/storage fees, ads, subscriptions, clawbacks, deductions). The Reserve column shows only when a listed row has one. The four always add up to Net, which equals the file's `total-amount` (the deposit).
- **Categories inside the columns** (migration `BreakOutSettlementExpenses`, `SettlementCategory` on each line): **Refunds** → *Refunded sales* (amount type `ItemPrice`/`ItemWithheldTax`: price, shipping, tax given back) and *Refunded expenses* (the rest: commission given back, `RefundCommission`, chargebacks, promotions). **Expenses** → first match wins: *Shipping* (`ShippingChargeback`, `ShippingHB`, Promotion/`Shipping`, `Inbound Transportation Fee`, `FBA Amazon-Partnered Carrier Shipment Fee`, `AWD Transportation Fee`), *Commission* (description `Commission`), *FBA fees* (transaction type `FBAFees`, descriptions starting `FBA`, `Storage Fee`, `StorageRenewalBilling`, `RemovalComplete`, `DisposalComplete`), *Other expenses* (everything else). The buckets themselves are unchanged, so the dashboard, Orders, and bookkeeping still read Sales / Refunds / Expenses / Reserve. Converted, `HomeOtherExpenses` and `HomeRefundedExpenses` take what is left of their bucket, so the parts always add up. The Settlements list keeps the four columns; the parts show on Summary and Lines (`SettlementBreakdown`, partial `_SettlementCategoryBreakdown`).
- **Ad costs**: `AdCosts` on the summary view is what Amazon **charged** for advertising in the settlement (`Cost of Advertising` + `Refund for Advertiser`, SKU-less lump sums; part of Other expenses, never added again). The list shows it as a column (sortable, `SettlementSort.AdCosts`, converted like every amount) and in the **ad costs card** (`_AdCostsTile`): the charged total, then **Ads API spend by family** (`IAdvertisingService.GetSettlementSpendAsync` → `IAdvertisingQueries.GetFamilySpendAsync`, `core.AdSpend`) over the local days the listed settlements cover (local day of the earliest period start through that of the latest period end, at most `AdvertisingService.MaxDays`), each family linking to the Advertising page. Spend is the selected marketplace's own (on the US list, CA's ad spend is not added), in its currency, and rarely equals the charge because Amazon bills ads later; the card says when the days reach outside the synced spend.
- **Deferred by Amazon** (`IDeferredPaymentService`, rules in Application `Settlements/Deferred*`; `IDeferredPaymentQueries` only returns rows): the Settlements list has a full-width tile (`_DeferredTile`) with what Amazon still holds for the marketplace (per currency, never summed across currencies), the order count, the next release, and *as of* the last successful deferred run (or "Not synced yet"). It links to `/Settlements/Deferred` (sidebar sub-link under Settlements): **one collapsible group per settlement the sales were made in** (`GetGroupsAsync`; settlements not imported yet — the open one — first, then newest period; a header with period, count, total, release range, still held, and a Summary link when the settlement is in this marketplace's list), each expanding into its transactions (`_DeferredRow`: order → Orders search, reason pill, posted, releases on with Held / Due / Paid out), at most `DeferredPaymentService.MaxGroupRows` (250) with a link to that settlement's full sortable list (`?settlement=`, `none` = no settlement); views *Still held* / *Paid out since* / *All* (`DeferredView`), search by order id, 10 groups a page.
- **Deferred out of each payout** (by `SETTLEMENT_ID`, read for every marketplace listed under the settlements list): the Settlements list has a **Deferred** column after Net payout; the Summary shows "deferred out of this payout" (amount, sales, still held) under the net, a **Deferred** column on each SKU row matched by (SKU, price each = |principal| ÷ quantity, as paid, like `SalePrice`), and a *Deferred out of this payout by SKU* list for every SKU/price (some have nothing paid in the settlement); Lines lists the row's deferred products (Held / Due / Paid out); the Dashboard payout card adds *Still deferred · until …* (the held part). Deferred money is **never part of Net or the settlement columns**. On the US list, CAD/MXN deferrals convert at the settlement's own `ExchangeRate` (as paid without a rate; price each always as paid). The Summary page shows a banner when the settlement paid out orders Amazon had deferred (released deferrals of its `Order` lines, read for every marketplace listed under it), and Lines marks such order groups *Was deferred · released …* (or *Deferred until …* while held). The Orders page shows *Deferred until …* instead of *Not paid out* for an unpaid order Amazon holds. Deferred amounts are **not** settlement money: they never enter the settlement columns or totals.
- **Settlement dates are the marketplace's local days** (`SettlementFormat.Period`/`Day` with the marketplace's zone; the dashboard's latest payout and the IIF entry too): Amazon closes North America periods around 01:53 UTC, the evening before locally, so UTC dates were a day late compared with Seller Central. Line posted dates are **not** converted (date-only, stored at midnight UTC). The exchange rate still uses the UTC deposit date.
- **Price each and Units**: `quantity-purchased` and `order-item-code` are kept on `stg.SettlementLine`/`core.SettlementLine` (migration `AddSettlementUnits`). *Price each* (`SalePrice`) = the Principal of an order item (settlement, order, order-item-code, SKU, transaction type) ÷ its quantity, so a 2-unit order at 20.00 joins the 10.00 row; *Units* = the quantity on the item's Principal line (0 on every other line, so sums count each item once). Refund lines carry no quantity, so refunds never reduce Units (the Refunds column shows the money). Settlement lines imported before the columns existed are filled by migration `BackfillSettlementUnits`, which reads the two fields from the raw lines kept in `stg.SettlementLine` (by position, only where the line's sku and amount match what was staged) and re-promotes each affected settlement; it is repeatable and does nothing once every settlement has quantities. ASIN/title come from `core.Product` by SKU (empty when the SKU isn't in the catalog).

## Orders page (`/Orders`)

- **List** (`IOrderService` → `IOrderQueries`, rules in Application `Orders/`): sales tiles over everything the filters select (Orders with cancelled count, Units, Sales, Avg order value; cancelled orders — both spellings, `OrderStatuses` — are counted but left out of units and sales, as in `rpt.vw_SalesLine`), a search where **every word** (`ProductSearch.Terms`) must match the order id or any item's SKU / ASIN / title, purchase dates in the marketplace's local days, a status select, and sorts Purchased / Units / Sales (`OrderSort`, natural directions in `OrderSorts`). Purchase times show in the marketplace's local time. Each order is a collapsible group (`[data-expand-row]`) of its items (`_ProductCell`, unit cost) and, once paid out, its settlement breakdown.
- **Paid out** (`OrderPayout`): the order's lines in `rpt.vw_SettlementLine` (so the bucket rule stays in the view), added up over **every** settlement that has them (a sale and its refund are often in different ones), **as paid** and only in the order's own currency. They are read from the marketplace's settlements list (`SettlementMarketplaceId ?? own`: Canada's orders find their CAD lines in the US list), the one place this page reads another marketplace's rows; settlement links show only where the list is the marketplace's own. `core.SettlementLine.AmazonOrderId` is indexed for this lookup.
- **Est. profit** (`OrderProfit`): paid out − Σ(units × the SKU's **current** cost in `core.ProductCost`). Only for paid-out orders: before payout the fees aren't known, and sales − cost would overstate it. An item without a cost → *Cost missing*; cancelled → none. Computed per page, so not sortable.
- **CSV** (`OrderCsvWriter`, `?handler=Export` with the same filters): one row per item, purchase time in local time with its offset, RFC 4180 quoting, text starting `= + - @` prefixed with `'` (formula injection), UTF-8 with BOM for Excel. At most `OrderService.MaxExportRows` (50,000) rows; a cut-short file says so in its name.

## Advertising page (`/Advertising`)

- **What it shows** (`IAdvertisingService` → `IAdvertisingQueries`, rules in Application `Advertising/`): Sponsored Products spend from `core.AdSpend` over a range of the marketplace's **local days** (default the last 30 days through yesterday, the last day synced; 7 / 30 / 90-day quick picks; at most `AdvertisingService.MaxDays` = 366), as **one collapsible group per product family** (by name, *No family* last) with its subtotal, a row per advertised SKU (`_ProductCell`, campaign count), and an *All listed* totals row. Tiles: Ad spend (clicks, cost per click), Ad sales (orders from ads), ACoS, TACoS. Family filter (`0` = no family), search where every word must match the SKU / ASIN / title / family (`ProductSearch.Terms`), and sorts within each family (`AdSort`, natural directions in `AdSorts`; a SKU whose ratio can't be worked out goes last either way). Everyone can view; it sits under Operations after Orders.
- **One figures shape** (`AdMetrics`) for SKU, family, and total rows, so subtotals are always the sum of their rows; ratios are recomputed from the sums, never averaged, and are "—" (null) without a divisor. **ACoS** = spend ÷ ad sales (Amazon's 7-day attribution). **TACoS** = spend ÷ every sale of the listed SKUs over the same local days from `rpt.vw_SalesLine` (cancelled left out), so it uses the Orders page's numbers. The figure cells are one partial (`_AdMetricCells`) so the three row kinds line up. The table stays narrow so it fits its card without the floating header: ACoS sits under Ad sales and TACoS under Total sales (both still sortable from the header), Impressions/CTR shows only from `xl`, and the product column (`.ads-table .product-col`) takes the remaining width with titles ending in "…".
- Spend is in the marketplace's currency (Amazon Ads bills each account in its own). Recent days change for about two weeks as Amazon credits sales; the toolbar says how far spend is synced (`GetSpendRangeAsync`). When the range starts before the first synced day (`AdvertisingReport.StartsBeforeSync`), total sales for TACoS start at that day too, and the toolbar says so, so unsynced days don't make ads look cheaper.

## Dashboard & UI conventions

- **Dashboard rules live in `DashboardService`** (Application, unit-tested); `IDashboardQueries` only returns rows (`rpt.vw_SalesLine`, settlements, sync health), and stock comes from `IInventoryService` (see below). Pages format, never compute.
- **Local business time**: days/hours use the selected marketplace's `TimeZoneId` (US `America/New_York`, CA `America/Toronto`, UK `Europe/London`), not UTC. Comparisons use the same elapsed time ("today so far" vs "yesterday until now").
- **Honest comparisons**: if synced Orders history (earliest successful run's `DataStart`) doesn't cover the whole comparison window, changes are suppressed (`ComparisonAvailable = false`) instead of showing misleading percentages.
- **One currency**: every page shows one marketplace, so money is always in that marketplace's currency (USD/CAD/GBP, formatted `$`/`CA$`/`£` by `DashboardFormat`; `MX$` for MXN payouts shown as paid). Amounts in different currencies are never summed as they are: CAD/MXN settlements in the US list are added only once converted (see *Exchange rates*).
- **Theme**: Light / Dark / System via `wwwroot/js/theme.js` (loaded in `<head>` to avoid a flash; choice in localStorage). Colors are CSS tokens in `site.css` defined per `[data-bs-theme]`; components must use tokens, never hard-coded colors. No inline styles or scripts (CSP) — charts are SVG with attribute geometry and token-colored classes.
- **Lists**: follow the Amazon sync page — clickable KPI tiles (`card tile`), `.search-box` + auto-submitting selects (`data-autosubmit-form`), bulk selection (`data-select-row`/`data-bulk-bar`), and confirm-before-submit (`data-confirm`) — all handled in `site.js`, `.segmented` view switches, a `.card-toolbar` above a `.data-table`, `.pill` statuses, `.empty-state`. The Inventory page splits wide data into views (Overview / Stock breakdown) instead of one very wide table. Their switches, filters, sorts, and pagers reload only the list (see *Partial reloads*).
- **Partial reloads** (`data-fragment`): a list page's changing section is a `_XxxBody` partial (model = the PageModel) rendered inside `<div data-fragment="name">`, and its `OnGetAsync` ends with `return this.PageOrFragment("_XxxBody")` (`Models/PageFragments`). site.js turns links to the same page and GET forms inside the section into a `fetch` of the **same URL** with the `X-Fragment` header, swaps the section, and pushes the address (Back/Forward re-fetch it; any failure loads the page normally). A header, not `?handler=`, so `LinkWith`/`CurrentFilters`, bookmarks, and the no-script path see the real URL; `?handler=` links (exports, downloads) and `[data-fragment-skip]` are never intercepted, and POSTs keep the full-page PRG. After a swap site.js sets up tooltips, sticky headers, and the bulk bar again; everything else it does is delegated on `document`, so a new section needs nothing more. Never put a `data-dirty-form` inside a section (a swap would discard unsaved edits), which is why Products and the Worksheet reload whole. Converted: Settlements (list, Summary with In USD | As paid, Lines, Deferred), Orders, Advertising, Inventory (Overview, Ledger, Awaiting Amazon), Bookkeeping.
- **Sidebar** (`Pages/Shared/_Sidebar.cshtml`): each category (Overview, Operations, Bookkeeping, Tools, Admin) is a native `<details class="nav-group nav-group-{key}" data-nav-group="{key}">`, so it works without script; a page with sub-pages keeps its own link and folds them in a nested `<details>` beside it (Inventory → Worksheet). The server opens only **Overview and the current page's category**. site.js remembers what the user opens or collapses (`aerai-nav-state`, a key → open map) but never closes the current page's category, and the login page (`data-nav-reset`) clears it, so every sign-in starts from that default. Category colors are `--nav-*` tokens set through `.nav-group-*` → `--nav-accent`; every category and link has an `_Icon`. The desktop **icon rail** (`data-nav="rail"` on `<html>`, key `aerai-nav`, applied early by `theme.js`) shows only the current page's category, visually hides labels as tooltips, and makes another category's icon open that category's first page; rail changes are never saved, and leaving the rail restores the full sidebar as it was. A new page gets a `NavLink(...)` line in its category (and its path in that category's "current" check).
- **Section tabs** (`.section-tabs`): an area with several peer pages shows them as one tab bar under the page title instead of toolbar link buttons. Inventory's is `Pages/Inventory/_InventoryNav.cshtml` (`InventoryNavModel`/`InventorySection`): Overview · Worksheet · Awaiting Amazon (open-send count, amber when any are overdue) · Ledger · Pictures, carrying the family in view to the pages that filter by it. The sidebar lists the same pages under Inventory (`inventorySubPages`), and deeper pages (Edit, bulk home stock, uploads, Families) keep a breadcrumb back instead. Toolbars hold only the page's own actions (count sheet, upload, print, log movement). A new top-level inventory page gets a tab, a sidebar sub-link, and an entry in `inventorySubPages`.
- **Responsive**: tables go inside `.table-responsive` (positioned, so hidden labels can't widen the page); long Amazon titles use `.cell-truncate` + `title` tooltip (inside a table also capped at `32cqi` of the table's width). Under 768px the sidebar collapses behind a CSS-only hamburger toggle (the rail is desktop-only).
- **Sticky table headers**: every `.table-responsive` gets one from site.js, no per-table CSS: the header sticks to the window as the page scrolls, never a scroll box. A table that fits its card gets `.is-sticky` (no overflow, so the header cells stick); a table too wide to fit keeps scrolling sideways and gets `.has-float-head`: a `.sticky-float` copy of its whole header placed over the real one, cell widths copied, following the sideways scroll both ways. The copy loses ids, names, and `data-*` behavior attributes (page scripts never find it), and a click on its links, buttons, or boxes is passed to the same element in the real header; it is rebuilt on resize, header text changes, and box changes. When the wrapper is a direct child of a `.card` whose `.card-toolbar` sits above it and it is that card's only table, the toolbar sticks too (`.has-sticky-head`, header offset `--sticky-head`). Without script tables just scroll sideways. Sticky left columns in thead (`th.product-col`, `th.select-col`, `th.sku-cell`) need `z-index: 3`.
- **Totals rows go at the top**: a table's totals are its header's **last row** (`<tr class="totals-row">` inside `<thead>`), so they stick under the column names (`--sticky-row1`) and are styled once (`.table > thead > tr.totals-row`). Never a `<tfoot>` or a first body row. Used by Settlement Summary and Lines, Advertising, the Bookkeeping review, and the Worksheet.
- **Razor gotchas**: inside a C# block only the first element on a line is markup — put sibling elements on separate lines. After any Razor compile error, other pages may report bogus errors (e.g. on `<partial model=...>`) from stale source-generator state: run `dotnet build-server shutdown`, delete `src/AERai.Web.UI/obj`, rebuild.

## Inventory, restock & alerts

- **States**: `core.InventorySnapshot` keeps Amazon's detail — `Available`, `InboundWorking/Shipped/Receiving`, `ReservedCustomerOrder/FcTransfer/FcProcessing`, `Unfulfillable` — plus unsplit `Inbound`/`Reserved` for sources without a breakdown (generic upload, a day without the reserved report). `InventoryStates` (Domain), `stg.ufn_NormalizeInventoryState`, the check constraint, and `rpt.vw_InventoryPosition` must agree. The view picks the latest date that has a non-reserved-reason state (the reserved report alone is not a full snapshot) and also lists SKUs held only at home (`SnapshotDate` null; the dashboard and alerts ignore them).
- **AWD**: `rpt.vw_InventoryPosition` adds `AwdOnHand`, `AwdInbound`, and `AwdReplenishment` (AWD → FBA in transit) from each marketplace's **latest AWD date as a whole**, so a SKU absent from the latest listing has none; AWD-only SKUs get a row (`SnapshotDate` null). `AwdSnapshotDate` is that marketplace-wide date (on every row), shown with the FBA date as *FBA as of · AWD as of* above the Inventory list. `AwdTotal` = on hand + inbound; `OverallTotal` = FBA (`AmazonTotal`) + AWD + home. The Overview table shows **Available in FBA** (`Available`), **Available in AWD** (`AwdOnHand`, total on hand including AWD-reserved units), and **Total available** (`AvailableTotal` = the two), each sortable. Replenishment is shown (Stock breakdown's *To FBA*) but never added to totals: those units also appear in FBA inbound once the transfer ships (confirmed on live data). AWD is not sell-through stock and does not feed restock plans or alerts.
- **Numbers live in `InventoryService`** (Application, unit-tested); `IInventoryQueries` only returns rows. Sales rate follows the rule the retired desktop app used: 90 local days ÷ days since the SKU's first sale in that window, unknown below 14 days or 5 units. **Sell-through stock** = available + inbound + FC transfer + FC processing (customer-order reservations are already sold; unsplit reserved, unfulfillable, and home stock are excluded). Days of inventory = sell-through ÷ rate. Each SKU gets one `StockStatus` (OutOfStock, RestockOverdue, RestockSoon within `Inventory:AlertLeadDays`, Healthy, NoSalesData, NotAtAmazon) that the Inventory page, the dashboard (out of stock / restock due), and stock alerts all use, so they always agree; filtering, sorting, and the status counts are done in `InventoryService.GetOverviewAsync` (`InventoryFilter`).
- **User-maintained item data**: families (`core.ProductFamily`, shared, unique ignoring case; managed on the Inventory page's Families dialog — create, rename, delete, and bulk *Set family* on ticked rows, where a new name creates the family — through `IProductFamilyService` and the operator-only `/Inventory/Families` handlers; deleting a family unassigns its SKUs; empty families are kept), pictures (`Product.ImagePath`, JPEG/PNG/WebP ≤ 2 MB checked by file signature, stored in the separate replaceable `product-images` container — `RawStorage:ProductImageContainerName` — and served only through `/Inventory/Image/{sku}`; set one at a time on Edit or in bulk on `/Inventory/Pictures` through `IProductPictureService`: **Pull from Amazon** looks up SKUs with an ASIN and no picture via `IAmazonCatalogGateway` — live `searchCatalogItems` v2022-04-01, 20 ASINs per call through `SpApiPipelineHandler`, MAIN image ≤ 1000 px downloaded by a token-less client from Amazon image hosts only; simulated/disabled like the reports gateway — at most `MaxAmazonDownloadsPerPull` per click and never touching a SKU that has a picture; **Upload** takes pictures or `.zip`s named after a SKU (exact, then case-insensitive if unique) or an ASIN (all its SKUs), replacing existing pictures. Every path stores through `SetImageAsync`, which reads at most 2 MB whatever the declared length), and per-marketplace **home stock** (`core.HomeStock`; 0 = no row) entered on Edit, the bulk page, the Worksheet, or a `.xlsx/.csv/.tsv` upload (`sku`, `home-stock`; ClosedXML reads `.xlsx` behind `ISpreadsheetReader`). The downloadable **count sheet** (`IHomeStockTemplateService` → `IHomeStockTemplateWriter`, ClosedXML) is that upload's exact layout: first sheet `sku` + `home-stock` (current counts, yellow, whole-number validation), then reference columns the upload ignores (title, family, color, Amazon stock, 30-day sales, send to Amazon), ordered by family → color → SKU, optionally one family; a second sheet has instructions. Values are written as typed cells, never formulas. **Uploading is preview → apply**: `PreviewHomeStockImportAsync` checks the sheet against current home stock and saves nothing (changes, unchanged count, rejected rows); the review page then calls `IHomeStockLedgerService.ApplyCountsAsync` with the movement type chosen for increases (Received from supplier / Count correction / Other) and for decreases (Shipped to Amazon / Count correction / Other), plus an optional reference, note, and date. The reviewed changes travel in one hidden field (`HomeStockCountPayload`, `sku⇥current⇥new` lines, re-validated on Apply). Apply runs in one serializable transaction and skips (reports) any SKU whose balance no longer equals the reviewed `current`. Editing is Operator/Admin only.
- **Restock plan** (`RestockPlanner`) leads with **what to send into Amazon**: our need tops Amazon stock up to the target cover (deadline = Amazon stockout − transit − safety); Amazon's recommendation is folded in (send the **larger** quantity, by the **earlier** date; a recommendation without a date is due today); the send is capped at home stock and the rest is `ShortAtHome`. **Supplier reorders** are planned from all stock (Amazon + home): order-by = when everything runs out − (supplier + prep + transit + safety); quantity = the larger of a target's worth and lead + target days minus stock on hand. `DaysUntilAction` (status, sort, alerts) is the earlier of the send and reorder deadlines; alerts only mention the reorder once it's within `Inventory:AlertLeadDays`. The Inventory list's Next step shows only the send (with Amazon's advice under it); reorders live on the Worksheet. Lead times are per (SKU, marketplace) in `core.LeadTimeProfile` with null fields falling back to `Inventory:*` defaults. Plans are computed on read, not stored. A SKU without a sales rate gets no plan, but Amazon's advice still shows. **Units sent but not yet visible at Amazon** (`InventoryPosition.PendingToAmazon`, see the ledger note) count as Amazon stock in the plan, days of inventory, and totals, and come off Amazon's recommended quantity (`max(0, qty − pending)`, since it predates the send), so a send isn't suggested twice while Amazon and our sync catch up.
- **Restock math** (all pure, unit-tested): demand is a `DemandForecast` — a base rate blended from the last 30 days (`RecentWeight` 60%) and the 90-day velocity (40%), each divided by the season factor of the days it was measured over — times a `SeasonalityIndex` learned **per family** (a SKU without one learns from its own sales) from the last 24 full months of `IInventoryQueries.GetMonthlyUnitsSoldAsync` (UTC months; each calendar month ÷ the average month, smoothed ½ itself + ¼ each neighbour, clamped 0.4–2.5, **flat until 12 full months** exist). Cover, stockouts, and order sizes are counted in expected sales day by day, so the same target days need more units ahead of wedding season; `RestockPlan.SeasonFactor` (null when flat) shows as *Season ×1.4* under the suggestion. **Rounding** is per family (`core.ProductFamily.SendMultiple`/`SendMultipleLarge`/`SendLargeFrom`/`OrderMinimum`/`OrderMultiple`, migration `AddFamilyRestockRules`, which set handkerchief families to 5s, 10s from 50, orders 100+ in 10s; edited in the Families dialog through `IProductFamilyService.SetRulesAsync`, which asks for an alert refresh): `RestockRules.RoundSend` goes to the nearest multiple (at least one), then rounds **down** to fit home stock (all of it when less than one multiple); `RoundOrder` rounds **up** to the multiple and the minimum (the minimum is **per SKU**). **Aging limits** (`StockLimits`): while Amazon reports `EstimatedExcess` the send is 0 (`HeldForExcess`); a send never leaves more than `Inventory:MaxAmazonCoverDays` (150, under Amazon's 181-day surcharge) of expected sales at Amazon (`CappedForAge`). Supplier orders are **not** limited or flagged for long cover: stock waiting at home is ours to store, so only what is sent into Amazon can draw storage fees.
- **Home-stock ledger** (`core.HomeStockMovement`, `IHomeStockLedgerService`, `/Inventory/HomeStock/Ledger`): accounting-style log — Received from supplier (+), Shipped to Amazon (−), Count correction (±, entered as the new counted total; the difference is recorded), Other (±, note required), Opening balance (one per SKU from the migration). The page opens **By action** (`HomeStockLedgerView`): one collapsible group per **save** — entries sharing `CreatedAt` and `CreatedBy`, which every save stamps once for all its rows (an edit's copy keeps the original's, so it stays in its action), with **sends to Amazon apart from the rest of the same save** (a Worksheet save can recount and send; the two list as two actions, so undoing the shipment never undoes the counts; a send edited into another movement keeps its logged time, so it moves to the other half of its save) — newest first, 20 a page (`IHomeStockLedgerService.GetActionsAsync`, `HomeStockLedgerAction`: its movement types, local date and time, who, entry/SKU counts, units in / out / net, reference, *Undo* / *Undone*), listing its newest `HomeStockLedgerService.MaxGroupRows` (250) entries; each group's **Print** (`data-print-group` in site.js) prints only that group. **Undo action** (`UndoActionAsync` → repository `ReverseActionAsync`, the same send / not-send split; `ReverseManyAsync`/`ReverseEntriesAsync` for the ticked rows' **Undo ticked**; the forms post the id as a field, because `asp-all-route-data` replaces an `asp-route-id` written before it) reverses every reversible entry of the save in **one serializable transaction, all or nothing**, all reversals stamped with one time (so the undo is itself one action); it is refused, naming the SKUs, when a SKU's net would go negative or a send Amazon already partly shows is in it (single `ReverseAsync` refuses that too), and units taken out are put back before units added are taken out so no balance dips part way. *All entries* is the paged list in logging order; filters apply to both, and the entry row is the shared `_LedgerEntryRow` partial. **Invariant: a SKU's entries add up to `core.HomeStock.Quantity`**, which stays the balance every reader uses. Every home-stock write goes through `HomeStockBalance.Apply` inside a **serializable** transaction (entry + balance together); the Edit page, bulk page, uploads, and the Worksheet log count corrections, and the Worksheet's send box logs **Shipped to Amazon** (`IHomeStockLedgerService.ShipToAmazonAsync`, through the same stale-checked serializable path as count-sheet apply). Entries are never edited or deleted — a mistake gets a **reversal** (same type, opposite units, `ReversesId`, one per entry; not for reversals or opening balances; refused if it would go negative). **Editing a row** on either ledger view (Operators: the row's edit button opens it in place via `?edit={id}`, so it works with partial reloads and without script; `IHomeStockLedgerService.CorrectAsync`) changes its movement type, units, and note as a **correction**: in one serializable transaction the entry is reversed and a corrected copy logged with `CorrectsId` (one per entry; edit the latest copy to edit again). Received is always +, shipped always −, count corrections and other keep the typed sign; Other needs a note. The copy keeps the original's date, reference, and `CreatedAt`/`CreatedBy` (so a send stays in its Awaiting Amazon group) and, for a send, its Amazon baseline and `ReconciledUnits` (it closes once Amazon shows every unit); a send can't drop below the units Amazon shows or stop being a send once Amazon shows part of it, and an entry that only now becomes a send is logged as of the edit (its `CreatedAt`/`CreatedBy`, so it is a new Awaiting Amazon group) with today's baseline. The reversal is written first so balances read in logging order; when that would dip below zero (some of the original's units have since gone out) the copy goes first and the two `BalanceAfter`s are swapped, so the copy always shows the count after the whole correction. Edits made before that rule are fixed by migration `FixLedgerCorrectionBalances` (`V020_LedgerCorrectionBalances/fix-correction-balances.sql`: swaps only pairs still showing the in-between count, so it is repeatable). The ledger lists show only the latest copy, with *Edited … by … · was …* from the reversal and the original (`HomeStockLedgerEdit`); the original and its reversal are hidden from the lists and group totals but kept. **Bulk change movement / undo** (Operators, both views; one timestamp for the whole change): tick rows — or a whole action with its group header's box (`data-select-group`) — and the bulk bar either undoes them (**Undo ticked**, all or nothing, a second submit button with its own `data-confirm`, which site.js prefers over the form's) or sets a movement type (*Change movement to…*, blank keeps each) and/or a note (blank keeps each note) on all of them (`IHomeStockLedgerService.CorrectReasonAsync`, at most `MaxBulkEntries` = 250). Each entry is its own correction with the single-edit rules and keeps its units (received/shipped take the new type's direction); entries that can't change are skipped and listed in the message. `BalanceAfter` follows logging order, so the list is ordered by id. **Sends pending to Amazon**: every Shipped to Amazon entry (Worksheet send box, Log movement, or a count-sheet upload logging decreases as Shipped to Amazon) stores `AmazonBaselineUnits`/`AmazonBaselineAt` — the SKU's FBA sell-through stock and that snapshot's receive time when logged, read outside the serializable transaction — and stays *pending* (`rpt.vw_InventoryPosition.PendingToAmazon` = units − `ReconciledUnits` of open, unreversed sends) until `IPendingSendService.ReconcileAsync` matches it. `SqlPromotionService` runs that after every Inventory/FbaInventory/FbaReservedInventory promotion (a failure is logged, never fails the promotion). `PendingReconciliation` (pure) only uses a snapshot received after the send, oldest first, partials allowed: a reference starting `FBA` is a shipment id and is matched by inbound units; otherwise the delta rule (sell-through now − baseline + units sold since the baseline snapshot, minus units already accounted for, including all units of id'd sends, so errors keep sends pending longer, never shorter). Each send also queues a Run now of the marketplace's FBA inventory + restock schedules (`IInventoryRefreshRequester`; nothing when Amazon isn't connected). Sends still open after `Inventory:PendingSendExpiryDays` (default 7) are flagged, never dropped; on `/Inventory/HomeStock/Pending` (*Awaiting Amazon*: search by SKU, title, or shipment id, family filter, and views All / Needs shipment id / To check via `PendingSendFilter`, all kept across its posts) (list partial `_PendingSends`, one collapsible group per **send** — `PendingSendGroup.GroupBySend`: the entries one save wrote share `CreatedAt` and `CreatedBy`, **newest send first** (the repository still lists oldest first, which reconciliation relies on) — headed by weekday, date, and time, who, SKUs, awaiting / sent units, and shipment ids, with **Cancel shipment** (`IPendingSendService.CancelShipmentAsync`: every send of the group reversed at once, all or nothing, refused once Amazon shows part of any); a group checkbox, `data-select-group` in site.js, ticks its sends, and a group with several sends lacking an id takes one for all of them) Operators add a missing shipment id (the one ledger field that may change, and only from null) to one send or, by ticking several, to all the sends in one shipment (`SetShipmentIdsAsync`, at most `MaxShipmentIdSends`; sends that already have a reference are skipped), mark a send **Received** (closes it, `ReconciledBy` = user), or **Cancel** one that never went out (a normal reversal; refused once Amazon shows part of it). Sends logged before migration `AddPendingToAmazon` are sorted by its `backfill-pending-sends.sql`: closed when the SKU's latest snapshot was received after them, otherwise kept pending with that snapshot as their baseline (a SKU never at Amazon gets a baseline of 0).
- **Colors & the Worksheet** (`/Inventory/Worksheet`, everyone can view; Operators edit home stock in place and type units sent to Amazon in the *Send to Amazon* column — the suggested send is the box's placeholder, the save bar takes an optional FBA shipment id as the ledger reference, saved sends show in the Amazon column as *+N sent, awaiting Amazon* until reconciled (see the ledger note), and a row may change its count **or** its send in one save, not both, since the order would be ambiguous): one family at a time (tabs), SKUs grouped by `Product.Color` in `ProductColors.DisplayOrder` (blue, navy, green, teal, pink, purple, then the rest — the printed count sheet's order; the enum's numbers are stored, so never reorder them) and, inside a color, by `WorksheetSkuOrder` (styles — the letters before the first digit — the family carries in several colors first A–Z, then one-off styles like SBP001BL; the count-sheet download uses the same order) — a fixed `ProductColor` palette, set on Edit or with the Inventory list's bulk **Set color** (`/Inventory/Colors`). A fixed palette because CSP forbids inline styles: each color is a `--c-*` token (light and dark values) applied via `.sku-color-*` classes that set `--sku`. Grouping and subtotals are `InventoryService.GetWorksheetAsync` (`InventoryWorksheet`/`WorksheetGroup`/`WorksheetTotals`). The family's **Total** row is the last row of the sticky header (a second `thead` row sticks under the first: site.js sets `--sticky-row1`), and its send cell shows **Sending N**, the live sum of the typed send boxes (`data-send-total`), with the suggested total under it (without script, the suggestion). The page prints cleanly (`@media print`); unsaved edits show a sticky save bar (`data-dirty-form` in site.js).
- **Alerts** (in-app only): `StockAlertService` raises **Out** for `StockStatus.OutOfStock` and **Low** for `RestockOverdue`/`RestockSoon`. A filtered unique index allows one open alert per (marketplace, SKU); a level change resolves the old alert and raises a new one so users are notified again. `StockAlertWorker` refreshes every active marketplace when asked through `IStockAlertRefreshSignal`, debounced 10 s. Promotion (`SqlPromotionService`), home-stock writes (`HomeStockLedgerService`, `InventoryItemService`), pending-send changes (`PendingSendService`), and lead-time edits all ask, so **any new writer of alert inputs must call `Request()`**. It also refreshes once every `Inventory:AlertRefreshMinutes` (default a day) for statuses that change only with time. Refreshes are idempotent and safe on several instances. Read state is per user email (`ops.StockAlertRead`); the top-bar bell (`_NotificationBell`) shows the current marketplace's unread count.

### Passwords (change / forgot / reset / login with code)
- **Change password** (`/Account/ChangePassword`, the email link in the top bar) requires the current password; other sessions are signed out within a minute (`SecurityStampValidatorOptions.ValidationInterval = 1 min`), the current one stays signed in.
- **Forgot → email → reset**: `IPasswordResetService` (Application) owns the rules: the same confirmation whether or not the account exists, no link for admin-locked accounts, single-use Base64Url tokens that expire after `PasswordResetService.LinkLifetime` (1 hour). A successful reset also clears a failed-attempt lockout.
- **Reset-poisoning guard**: emailed links are built by `PublicUrl` from `App:PublicBaseUrl` (required outside Development), never from the request Host header.
- **Abuse limit**: forgot-password POSTs are rate-limited to 5 per 15 minutes per client IP (`RateLimits.PasswordReset`).
- **Login with code** (`/Account/LoginWithCode` → `/Account/VerifyCode`, the button under *Sign in*): `ILoginCodeService` (Application) emails a one-time 6-digit code that signs in without a password. Rules: same response whether or not the account exists; one outstanding code per account (a new one replaces it), valid `LoginCodeService.CodeLifetime` (10 min), at most one per `ResendCooldown` (60 s, a request inside it sends nothing); `MaxAttempts` (5) wrong guesses discard the code, and every wrong guess also counts toward the normal Identity lockout; locked accounts (admin or failed attempts) get no code. Only a **hash** of the code is stored, in Identity's `AspNetUserTokens` (`AERai`/`LoginCode`), so there is no table of its own. The email moves between the two pages in TempData, never the URL. POSTs are rate-limited per client IP: `RateLimits.LoginCode` (send/resend, 5 per 15 min) and `RateLimits.LoginCodeVerify` (20 per 15 min).
- **Show password**: every password box is an `.input-group` with `<partial name="_PasswordToggle" />` (eye button, `data-password-toggle`, handled in site.js; hidden without script). Use it on any new password field.
- **Email**: `IEmailSender`, chosen by `Email:Provider`: `Resend` → `ResendEmailSender` (Resend's HTTP API, key `Email:ResendApiKey`, Key Vault `Email--ResendApiKey`; the From domain must be verified in Resend) in Azure, `Smtp` (default) → `SmtpEmailSender` (MailKit) locally against Mailpit (`docker compose`, inbox at http://localhost:8025). Never log email bodies (they contain reset links and sign-in codes). A missing `Email:Host` (SMTP) or `Email:ResendApiKey` (Resend) disables email with a warning.

## Products & COGS (`/Products`)

- **List**: tiles All / Missing cost / Cost set (`ProductCostFilter`; counts follow the search and family, not the tile, via `IProductRepository.GetTotalsAsync`), family filter, sortable columns (`ProductSort`, natural directions in `ProductSorts`; blanks always last), and a search where **every word** must match the SKU, ASIN, title, or family name (`ProductSearch.Terms`, at most 5 words). Pictures use the shared `_ProductCell` partial (also used by Inventory) and `/Inventory/Image/{sku}`; the title links to Inventory → Edit for Operators.
- **Inline edit** (Operators): each cost is a box in the table (`data-dirty-form` save bar). The form posts every box with its original value; only changed ones become `ProductCostChange`s and go to `IProductService.SaveCostsAsync`, which rounds to cents, keeps a SKU's last change, drops no-ops, and **skips (reports) a SKU whose stored cost no longer equals the original** (`ApplyCostsAsync`, one serializable transaction). Blank clears a cost. `ProductCostText` is the one parser (accepts `$`, `CA$`, `£`, thousands separators; 0–`MaxCostOfGoods`). `Products/Edit` (single SKU) still exists for deep links.
- **COGS sheet** (`/Products/Upload`, `IProductCostTemplateService` → `IProductCostTemplateWriter`, ClosedXML): first sheet `sku` + `cost-of-goods` (yellow, decimal validation), then reference columns the upload ignores (ASIN, title, family, cost last set), ordered family → SKU, optionally one family; typed cells, never formulas. **Upload is preview → apply** like the home-stock count sheet: `PreviewCostImportAsync` saves nothing (new / changed / unchanged / blank / rejected); Apply carries the reviewed changes in one hidden field (`ProductCostPayload`, `sku⇥current⇥new`) into the same `SaveCostsAsync` stale check. **A blank cost cell leaves the cost alone** (clearing is done on the page), so a partial sheet never wipes costs. `UploadedSheet.ReadAsync` is the shared .xlsx/.csv/.tsv reader for spreadsheet uploads.

## Bookkeeping (QuickBooks Desktop export)

- **What it does**: turns one settlement (`core.Settlement`/`core.SettlementLine`) into a QuickBooks Desktop **IIF general journal entry** — one `TRNS` line for the marketplace's deposit account (the net payout) balanced by one `SPL` line per QuickBooks account. Pages under `/Bookkeeping` (Operator): **QuickBooks export** (`Index`: settlements with an *Exported* pill, the generated files, download), **Review & export** (`Settlement/{id}`: every kind of amount with its account, unmapped ones flagged, Export button), and **Account mapping** (`Mapping`: the accounts and the deposit account). Rules live in `BookkeepingService`, `SettlementPreviewBuilder`, and `IifExportGenerator` (Application, unit-tested); `IBookkeepingQueries`/`IBookkeepingStore` (one `BookkeepingRepository`) only read and write rows.
- **Mapping key** is Amazon's own `(amount-type, amount-description)` pair, so grouping follows exactly what Amazon reports instead of a hard-coded scheme; a blank amount type falls back to the row's transaction type. Several pairs may share one account and are summed. A settlement with any unmapped pair, or whose marketplace has no deposit account, **cannot be exported**. Mappings (`core.BookkeepingAccountMapping`) are **shared by all marketplaces** — the chart of accounts belongs to the company — which is the one deliberate cross-marketplace read (`IBookkeepingQueries.GetCategoriesAsync`); the **deposit account** (`core.BookkeepingSettings`) is **per marketplace** because each is paid in its own currency, usually into its own bank account. Account names are trimmed, capped at 200 characters, and may not contain tabs or line breaks (they would split an IIF line).
- **The entry balances by construction**: net payout is the sum of every settlement line (as in `rpt.vw_SettlementSummary`) and each `SPL` is the negation of its account's total, so there is no adjustment line. The entry is dated the settlement's period end in the marketplace's local time (`SettlementBooks.TimeZoneId`; the date Seller Central shows).
- **CAD/MXN settlements export in USD** (the marketplace's currency, so they post into the US books): `SettlementPreviewBuilder` converts each account's total at the settlement's rate (same rule as `rpt.vw_SettlementRate`, read by `BookkeepingRepository`), the deposit line is the converted payout (the Operator's amount received when given), and the cent or two the roundings leave is added to the largest account line (`RoundingAdjustment`, shown on the review page). The memo records the original amount and rate (`CAD 81.51 at 0.72 USD (ECB 2026-09-16)`), and `core.BookkeepingExport` keeps `OriginalCurrency`/`OriginalNetTotal`/`ExchangeRate`. A settlement in another currency **without a rate cannot be exported**. Debit/credit signs follow the retired desktop export; **test-import a generated file into a QuickBooks sample company before trusting it for real books.**
- **Files are stored, not written to disk** (`core.BookkeepingExport`: file name, the IIF text, deposit account used, net, period, who/when). Re-downloading returns exactly what was handed over even if the settlement is later re-promoted; exporting twice creates two rows. Downloads are scoped to the current marketplace and sent as UTF-8 without a byte-order mark, CRLF line endings.

## Secrets & configuration

- Never commit secrets. Local: `.env` (gitignored, copied from `.env.example`) for Docker, `dotnet user-secrets` for the UI project.
- Amazon credentials: `SpApi:ClientId`, `SpApi:ClientSecret`, `SpApi:RefreshToken`, optional `SpApi:Europe:RefreshToken` (used now) and `AmazonAds:ClientId`, `AmazonAds:ClientSecret`, `AmazonAds:RefreshToken` (optional `AmazonAds:EuropeRefreshToken`) for the Ads spend sync; no profile id (found automatically). `scripts/set-local-secrets.sh` sets `AmazonAds:Mode=Live` when all three are entered. Locally set them (and optionally `ConnectionStrings:Sql`) with `scripts/set-local-secrets.sh` (hidden prompts → user-secrets); in Azure they are Key Vault secrets named with `--` (e.g. `AmazonAds--RefreshToken`), and Bicep sets `AmazonAds__Mode=Live`.
- Email (Resend): `Email:ResendApiKey` (user-secrets via `scripts/set-local-secrets.sh`, which also sets `Email:Provider=Resend`; Key Vault `Email--ResendApiKey`).
- Exchange rates: `ExchangeRates:Mode` (`Live` default, `Simulated`, `Disabled`) and `ExchangeRates:BaseUrl` (Frankfurter); no key needed.
- Connection string key: `ConnectionStrings:Sql`. Raw storage: `ConnectionStrings:RawStorage` (`UseDevelopmentStorage=true` for Azurite, set in `appsettings.Development.json`) or, in Azure, `RawStorage:ServiceUri` with managed identity (storage account has shared keys disabled). The same account holds the `raw` and `product-images` containers; both are created at startup if missing. Dev admin seed: `Seed:AdminEmail` / `Seed:AdminPassword` (only seeded when both are set).
- Azure: Key Vault via managed identity (`KeyVault:Uri`), Azure SQL with Entra-only auth (managed identity, no SQL password).
